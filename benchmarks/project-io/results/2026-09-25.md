# 工程开启与保存压力测试（2026-09-25）

本篇是启用 `serde_json/float_roundtrip` 和四项读写优化前的合成数据基线。修复后的真实大型模型结果见 [同日真实模型压测](2026-09-25-real-model.md)。

## 结论

目前不需要开始迁移到二进制工程格式。真实样本的 0.77 MB 清单打开约 32 ms、重复保存约 51 ms；把网格和绑定扩到 23.5 MB 后分别约 144 ms、288 ms。极端的 94 MB 合成清单达到约 882 ms、1,071 ms，且进程峰值内存约 688 MB，表明超大工程值得优化，但尚不能把这归因于 JSON 格式本身。

优先改进当前路径：`decode_project` 构建网格时，`create_mesh` 对每个新网格线性扫描已有网格检查 `runtime_id`，网格数增大时呈二次成本；保存对同一文档编码两次，并对全部 PNG 重新读取和解码。若真实用户工程经常接近 100 MB，或产品要求开启和保存稳定低于 500 ms，应先测这些优化，再以真实数据做二进制原型对照。

## 方法

- 环境：Apple M4、16 GB 内存、macOS 27.0.0、本机 APFS；`cargo build --release` 优化构建。
- 基底：本机 `output/head-xy-experiment/result/project` 的现有可编辑工程，清单 0.77 MB，24 个网格、23 个绑定、24 张 PNG（合计约 2.6 MB）。`output/` 被 Git 忽略，基底需在同一工作区保留才能逐字复现。
- `tools/make_project_stress_fixture.py` 复制网格、绑定和 Keyform，重写 UUID、运行时 ID 与网格引用，素材硬链接复用；倍率 1、4、16、32、64、128。最大档有 3,072 个网格、2,944 个绑定。复制相似数据使压缩率偏高，因此不以合成数据的压缩率论证格式选型。
- `project_io_stress` 使用 `DocumentSession::open_authoring` 和 `DocumentSession::save` 测量完整路径，包括 PNG 校验、清单落盘和同步；单独测 `decode_project`、`encode_project`。`decode_project` 包括 JSON 校验、反序列化和 Document 构建，并非纯 JSON 解析器耗时。每档重复 5 次，最大档重复 3 次。表中为中位数，重复保存排除首次创建文件的样本。保存后重新打开，并验证文档内容相等、资源诊断为空。内存为 `/usr/bin/time -l` 统计的整次进程峰值。
- 运行期间文件系统缓存为热态；数字不代表首次启动应用、网络盘、冷缓存或 Godot 界面耗时。

| 128 | 93.97 | 3,072 / 2,944 | 680.5 | 107.8 | 882.4 | 1,071.1 | 688 |

另将基底的一张素材替换成 4096 × 4096、约 7.8 MB 的 PNG。清单仍为 0.77 MB，全部 PNG 约 10.8 MB；完整打开中位数从 31.8 ms 增至 83.3 ms，重复保存从 51.0 ms 增至 122.3 ms，峰值内存从 66 MB 增至 193 MB。这个对照显示素材处理会主导常见体量的读写。

对最大档另做了不改格式语义的紧凑 JSON 对照：清单从 93.97 MB 降至 26.02 MB，完整打开中位数从 882 ms 降至 694 ms；当时的保存器仍输出排版后的 93.97 MB 清单。真实基底的紧凑 JSON 约 0.22 MB；Zstandard level 3 压缩约 54 KB。合成数据高度重复，故不报告其压缩率作为真实工程预测。

## 判断边界与复现

本次没有实现或测量二进制 codec，因此不能宣称二进制格式的实际速度或节省比例。现有 JSON 的内存峰值和超大工程开启耗时是后续性能工作的重点；迁移格式还会增加版本兼容、损坏恢复与可检查性成本。建议先让真实作品规模数据触发格式评估，再用同一批工程比较完整生命周期、内存、文件体积和往返一致性。

```sh
python3 tools/make_project_stress_fixture.py output/head-xy-experiment/result/project target/project-io-stress/example-input 32
cargo build --release -p kasane-project --example project_io_stress
target/release/examples/project_io_stress "$PWD/target/project-io-stress/example-input" "$PWD/target/project-io-stress/example-save" 5
```

原始逐次计时保存在被 Git 忽略的 `target/project-io-stress/result-*.json`，首次保存耗时也在其中。`cargo test --release -p kasane-project`：39 项测试通过。

四项读写优化后，用同一 3,072 网格输入又测了 3 次：旧排版清单的完整打开中位数 860 ms（原基线 882 ms，差距较小），保存后的清单为 26,019,942 字节，重复保存两次为 255 ms 和 264 ms（原基线中位数 1,071 ms），重开后内容相等。索引去掉了网格运行时 ID 校验中的线性扫描，但这个规模下完整打开仍主要受其他工作影响，不能把 22 ms 差异单独归因于索引。逐次数据见 `target/project-io-stress/after-fix-synthetic-128-bench.json`。
