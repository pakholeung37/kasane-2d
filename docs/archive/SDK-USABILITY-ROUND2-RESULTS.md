# SDK 创作可用性：第二轮类型检查对照

日期：2026-09-24。目标是检验“把 Pyright 加入 Python 创作脚本交付流程”是否改善交付脚本的静态正确性。此轮沿用[第一轮](SDK-USABILITY-RESULTS.md)的同一局部编辑任务，但**不合并两轮成绩**。

## 设计

三个独立的 `gpt-6-luna` subagent，均无先前试验对话；一个对照、两个实验。全部使用相同的 CPython 3.14/macOS arm64 CPU wheel、已安装 `kasane` 的 Python、`SDK-API.md`、任务目标和内容相同的输入工程。Git HEAD 为 `0aa822a`，wheel SHA-256 为 `b8665e694bb0ee3caf123abcb25b0a9ade27ed7282ed4114fa69415fc32cc333`，三份输入 manifest SHA-256 均为 `fb065b2e8c7690dbf16f27b09dba722979769faf545ec53baa641f590dcac266`。

对照组收到第一轮格式的任务，实验组仅额外收到“提交前用 Pyright 1.1.414 检查脚本，通过后运行并重开工程验证”的指令。任务包的其他差异只是各自的输入和输出路径。没有向受试者提供[类型速查](SDK-PYTHON-TYPING.md)、源码、现有 recipe、测试或判分器。主持人事后对**全部三份**脚本运行同一 Pyright 命令，并用同一独立判分器检查工程。受试者笔记中的时间和查阅范围为自报，未做完整命令轨迹审计。

原始任务包、脚本、笔记、工程、输入元数据、判分 JSON 和 Pyright JSON 保存在本地 `target/sdk-usability/2026-09-24-second-round/`；该目录不纳入 Git。判分使用 `tools/evaluate_sdk_usability.py`，其中 36 项检查涵盖输入不变、结构、资源、非目标内容、目标 keyform 和求值采样。

## 结果

| 条件 | 自报用时 | 工程判分 | 事后 Pyright 错误 | 原输出路径直接复跑 |
| --- | ---: | ---: | ---: | --- |
| 对照 | 约 2 分钟 | 36/36 通过 | 3 | `DESTINATION_EXISTS` |
| 要求类型检查 1 | 85 秒 | 36/36 通过 | 0 | 通过 |
| 要求类型检查 2 | 63 秒 | 36/36 通过 | 0 | `DESTINATION_EXISTS` |

对照脚本的三个错误来自同一处：`session.parameter(...)` 可能返回 `None`，却直接访问其 `name`、`minimum`、`maximum`。两份实验脚本在受试者自行检查和主持人事后复核时均为 **0 个 Pyright 错误**。三份工程都可重开并通过全部状态检查，说明类型检查没有妨碍完成任务。

直接复跑指的是**不清理首次输出、再次运行同一脚本**。实验 1 主动清理其自行生成的结果目录，因此通过；对照和实验 2 都因结果 manifest 已存在而失败。失败时已有正确工程仍可由判分器重开。这重复了第一轮发现的保存路径问题，也表明 Pyright 无法处理这种运行时状态。

## 能得出的结论

这轮结果**支持把静态类型检查纳入脚本工作流**：同一 Luna 模型、同一 wheel、同一输入下，要求检查的 2/2 份交付脚本无静态错误，而未要求检查的 1/1 份留下了可检测错误。已有 wheel 的 `py.typed` 和标注在此轮之前就能报出这类问题，因此证据针对的是**检查步骤及执行要求**，不能归因于本轮文档注释或 wheel 代码的变化。

样本只有一份对照和两份实验，且只有一个任务；它不足以证明总体成功率或用时改善。自报时间也不足以做速度结论。工程正确性三组相同，观察到的改进限于脚本静态质量。后续应在新建工程和依观察结果修正的任务上重复对照，并记录自动化的命令与错误轨迹；保存流程的可重跑性需要单独改进和测试。
