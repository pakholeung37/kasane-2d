## 观察到的使用障碍

1. **保存到已有目标的语义反复造成重试。** 四位受试者在自己的试验中遇到 `DESTINATION_EXISTS`；第五位在主持人直接复跑时也遇到。保护已有工程的拒绝行为合理，但当前任务需要使用者自行设计唯一输出路径或清理自身产物。成功脚本采用三种不同办法：清理自己的结果目录、删除自身旧 manifest、每次生成新目录。文档应给出清晰的可重跑保存模式，并解释何时需先打开已有工程。
2. **Python 接口形态不容易从当前 SDK 文档确认。** 两位受试者把属性当方法调用；一位把 `open_project` 当 Session 方法；一位误用 `SaveResult.manifest_path`。这些都靠运行时签名或异常恢复。当前 [SDK-API.md](SDK-API.md) 以 Rust 契约和阶段记录为主，缺少紧凑的 Python `Session`、`Edit`、快照及保存返回值参考。
3. **数据类型表达需要例子。** 一位把 `Point` 当双参数构造器；另一位尝试 `dataclasses.replace` 修改 `MeshKeyform`。实际 Python 对象是 tuple/named tuple 风格；文档可用一个读取旧 keyform、复制其非几何字段、替换位置的最短例子说明。
4. **重开后的快照 `version` 是新的会话版本。** 一位最初直接比较快照导致断言失败，后改为比较内容字段。需要在 Python 快照说明中明确这个常见验证方式。

优先处理文档和 API 可发现性，再复测同一任务与新任务。首轮已达预设探索目标，但不能据此宣称 SDK 整体可用：这里只有一个任务、一个模型设置、一个 wheel/平台，参与者的命令次数和首次有效 edit 时间未被自动记录。受试者的材料读取范围依据任务约束与自报，未做完整进程审计。下一轮应自动记录命令/异常轨迹，并加入从素材创建和依观察图修正两个任务；若改动文档或 SDK，成绩与本轮分开比较。

## 事后类型检查

首轮任务没有要求运行静态类型检查。事后用 Pyright 1.1.414 检查已安装 wheel 与五份最终脚本：第 2 份为 0 个错误；其余四份共 6 个错误，主要是对可能为 `None` 的查询结果直接访问字段，第 3 份还保留了一个 `hasattr` 保护下对不存在的 `SaveResult.manifest_path` 的引用。另写最小误用样例复现首轮出现的属性当方法、`Point` 双参数构造、`dataclasses.replace(MeshKeyform)` 和错误保存返回字段，Pyright 在执行前全部指出。

这说明 wheel 的 `py.typed` 与现有标注已经能拦截这些用法；首轮缺的是把类型检查加入脚本工作流。新的 [类型速查](SDK-PYTHON-TYPING.md) 和任务模板已加入固定版本 Pyright 命令。`DESTINATION_EXISTS` 仍须通过保存流程和文档解决，静态类型检查无法判断目标路径是否已存在。此修改属于**下一轮实验条件**，不改写首轮成绩。

该条件的三位 Luna subagent 对照结果见[第二轮报告](SDK-USABILITY-ROUND2-RESULTS.md)。
